# KOVARI — Mobile Production Bug Tracker (Phase 1)

This tracker maps confirmed production bugs discovered during the manual QA validation phase. All items must be forensic-investigated and given separate fix/hotfix cards.

| Bug ID | Module | Platform | Severity | Expected Behavior | Actual Behavior | Root Cause Analysis | Action |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **BUG-A1** | Auth | Mobile | P3 | User gets clear formatted error on invalid credentials; local client-side validation detects invalid email format. | Displays generic "Exception: email login failed" string; allows malformed email request submission. | `AuthService.loginWithEmail` catches failure and throws generic `Exception` instead of parsing API response error field or passing exception down, causing `ApiErrorHandler` to fall back to generic string formatting. | Create separate engineering task to enforce standard email regex validation on client and pass API error body messages correctly in `AuthService`. |
| **BUG-A9** | Auth | Mobile | P3 | Incorrect OTP displays a specific user-friendly error (e.g. "Incorrect verification code. Please try again."). | Displays generic "Exception: OTP verification failed". Resend and correct OTP flow work correctly. | Same root cause as BUG-A1: `AuthService.verifyOtp` (or equivalent) wraps the caught error in a generic `Exception` instead of re-throwing the `DioException` or parsing the API error body. | Bundle fix with BUG-A1 in a single error-handling improvement task across all `AuthService` methods. |
| **BUG-A7** | Auth | Mobile | **P1** | Reset link in email opens the app directly to the `/reset-password` screen, carrying the token. | Reset link is invalid / does not open in the app. Password cannot be changed. | **Two-part failure**: (1) The backend generates `kovari://reset-password?token=...` only when `platform=mobile` is sent — confirmed the mobile `AuthService` correctly sends `'platform': 'mobile'`. (2) The `AndroidManifest.xml` registers `kovari://reset-password` as a custom scheme intent-filter, which is correct. However, **there is no deep link listener in the Flutter app** (no `app_links`, `uni_links`, or equivalent package found in `pubspec.yaml` or any source file) to catch the incoming URI and route it to GoRouter's `/reset-password` screen. The link opens in the browser (or silently fails) because the Flutter layer has no handler to intercept it and extract the token. | **P1 Engineering task**: Add `app_links` (or `uni_links`) package, wire an `AppLinks().uriLinkStream` listener in the app's root widget, and redirect to `ResetPasswordRouteData` with the extracted token on `kovari://reset-password` URIs. |
| **BUG-A10** | Auth | Backend | **P2** | After account deletion, re-login with the same credentials must fail with a clear "Account not found / deleted" error. | Login succeeds with deleted credentials and redirects to Onboarding, meaning the account is not truly locked out post-deletion. | The `/api/auth/login` `handleStandardLogin` path (lines 119–123 in `login/route.ts`) selects only `banned, ban_reason, ban_expires_at` — it **does not select or check `isDeleted`**. The delete-account flow correctly sets `isDeleted: true` and nullifies `password_hash`, so `bcrypt.compare` against a null hash should return false — however the **user row is matched first via email** (line 122: `.ilike("email", email)`). The delete-account route also nullifies `email` on the user row (line 130: `email: null`), so the email lookup should fail. The re-login succeeding suggests either the email nullification is not completing (DB trigger or race condition) or the matched row still has the email. Either way the `isDeleted` guard must be added to the login query as a defence-in-depth check. | **P2 Engineering task**: Add `.eq("isDeleted", false)` filter to the Supabase login query in `handleStandardLogin` (and the web path) so deleted accounts are unconditionally blocked at login, regardless of email/password_hash state. |
| **BUG-E5** | Explore | Mobile + Backend | **P2** | Group cards in the Explore Groups feed render completely and instantly with name, cover image, destination, description, member count, trip dates, creator details, tags, languages, and lifestyle policies. | Group cards not rendering correctly or completely. Results not showing instantly. | **Two-layer field mismatch**: (1) `groupTransformer.ts` (backend) outputs `image` and `avatar` for the cover image field, but `GroupModel.fromJson` (mobile, `group.dart`) reads `coverImage` / `cover_image`. The transformer never outputs `coverImage`, so `group.coverImage` is always `null` → cover image never loads. (2) The transformer also omits `description`, `tags`, `languages`, `smokingPolicy`, `drinkingPolicy`, and `dateRange` (date_range) from its output. `GroupMatchCard` renders all of these fields conditionally — when all are null the card shows skeletal/empty sections. (3) For instant rendering: `matchGroups` response goes through a Redis SWR cache (`v1-stable-groups-v10`). On first load there is no cache, so the path hits the DB fallback synchronously — no disk/memory pre-seed like Solo mode's hydration engine — causing visible latency. | **P2 Engineering task**: (a) Fix `groupTransformer.ts` to output `coverImage`, `description`, `tags`, `languages`, `smokingPolicy`, `drinkingPolicy`, and `dateRange` (mapped from DB columns `cover_image`, `description`, `tags`, `languages`, `smoking_policy`, `drinking_policy`, `start_date`/`end_date`). (b) Fix `GroupModel.fromJson` to also accept `image`/`avatar` as fallback cover image keys. (c) Consider pre-seeding `ExploreState.groupMatches` from the local seen-user cache equivalent, or implement optimistic skeleton-to-content transition parity with the Solo feed. |
